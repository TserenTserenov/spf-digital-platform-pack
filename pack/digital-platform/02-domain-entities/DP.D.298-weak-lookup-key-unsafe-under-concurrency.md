# DP.D.298 Позиционный/эвристический ключ небезопасен при параллельной записи

## Правило

Lookup-key, идентифицирующий целевое состояние по позиции (порядковый номер) или по эвристике (тот же владелец, но не тот же слаг), а не по точному/контент-адресуемому идентификатору, даёт систематический риск при параллелизме: слияние по такому ключу выбирает «последнего/ближайшего», а не «правильного».

## Проявление 1 — конфликт публикации общего документа (merge-семантика)

Два параллельных агента заняли один порядковый номер фазы в общем документе — конфликт-резолвер публикации отбросил содержимое одной стороны вместо трёхстороннего слияния. Потеря невидима локально (рабочее дерево автора всё ещё показывает его содержимое) и всплывает только при сверке опубликованного состояния с origin постфактум.
**Фикс:** контент-адресуемый/уникальный идентификатор для новых разделов, либо гарантия настоящего трёхстороннего слияния (не last-writer-wins) на пути публикации; сверять с origin после любой публикации, где был конфликт.

## Проявление 2 — fallback-поиск по родственному, не идентичному ключу (порядок веток)

Fallback-поиск терминальности сессии по ВЛАДЕЛЬЦУ (не по точному слагу) маскировал СОБСТВЕННУЮ отменённую карточку того же слага более старой завершённой карточкой того же владельца.
**Фикс:** fallback-путь по родственному, но не идентичному ключу обязан быть строго уже основного пути — срабатывать только когда основной путь по точному ключу гарантированно пуст, и располагаться в коде ПОСЛЕ всех веток, которые могут дать самодостаточный ответ по точному ключу.

## Тест

«Ключ, по которому ищется/сливается состояние, — точный/уникальный идентификатор или позиция/эвристика (номер по порядку, тот же владелец)?» Позиция/эвристика при параллельном доступе → риск слияния не туда или подмены состояния более широким/старым совпадением.

## Применимо к

Любая система с параллельной записью в общий документ/состояние по позиционному или эвристическому ключу — не только git-публикация и session-guard.
