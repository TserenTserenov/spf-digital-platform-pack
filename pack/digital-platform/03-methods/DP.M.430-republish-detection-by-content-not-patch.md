# DP.M.430 — Распознавать «республикацию» сравнением итогового содержимого, не патча

## Определение

Скрипту, которому нужно распознать «этот коммит — просто республикация уже применённого в другом месте» (проверка на no-op/эквивалентность патча), нельзя доверять сравнению СЫРОГО ПАТЧА коммита с эталоном — патчи могут отличаться по контекстным строкам, порядку hunk'ов или представлению даже при идентичном итоговом содержимом файлов, и могут случайно совпасть при разном содержимом. Надёжная проверка — сравнение итогового СОДЕРЖИМОГО файлов напрямую.

## Отдельная находка: «простое» не значит «безопасное»

Сама функция выглядела «псевдо-простой» (короткий shell-сниппет), но шесть независимых раундов ревью нашли по реальному дефекту в каждом: сохранение прав доступа (mode), проброс exit status, обработка смены типа (файл→symlink), glob-инъекция через неэкранированный pathspec, недостаточное различение ошибок, инъекция через кавычку в обработчике trap.

## Переносимый принцип

1. Проверка идемпотентности/no-op должна идти по семантическому конечному состоянию (содержимое файла), а не по синтаксическому диффу.
2. Короткие shell-сниппеты, трогающие git plumbing, trap или pathspec, заслуживают нескольких состязательных раундов ревью — «простое» не значит «безопасное».

## Тест обнаружения

«Скрипт определяет no-op/республикацию сравнением сырого патча/диффа коммита?» Да → патчи с разным текстом могут иметь идентичное итоговое содержимое (или наоборот) — сравнивать итоговое содержимое файлов, не синтаксис патча.

## Отличие от смежного
- **DP.FM.354/DP.FM.133 (backup-restore, 3-way merge):** те про восстановление/слияние состояния из бэкапа; здесь — про способ ДЕТЕКЦИИ отсутствия реального изменения перед публикацией. Соседняя область (обе про сравнение состояний файлов), но разная задача — не дубли.

## Применимо к
Любой скрипт межмашинной/межрепозиторной публикации, определяющий «нужно ли вообще коммитить/пушить это изменение».
